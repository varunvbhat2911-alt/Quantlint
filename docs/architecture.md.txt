# QuantLint System Architecture

**Version:** 1.0

**Status:** Active

**Last Updated:** August 2026

---

# Overview

QuantLint is an AI-powered Quality Assurance platform designed for algorithmic trading strategies.

Its purpose is to help traders, developers, and quantitative researchers verify that a trading strategy is technically correct, statistically valid, financially realistic, and safe before it is backtested, paper traded, or deployed.

QuantLint is **not** a brokerage platform, an exchange, or an automated trading system.

The platform focuses on validation, analysis, explainability, and research.

---

# Vision

QuantLint aims to become the industry's standard quality assurance platform for algorithmic trading strategies.

Instead of helping users generate trading strategies, QuantLint helps users understand whether their strategies are trustworthy.

Every strategy uploaded to QuantLint should answer five fundamental questions:

- Is the code technically correct?
- Does the strategy contain statistical mistakes?
- Is the risk acceptable?
- Is the backtest realistic?
- Is the strategy ready for deployment?

# Architecture Goals

The system has been designed around the following goals.

## Modularity

Every subsystem should have a single responsibility.

No component should depend directly on another component's implementation.

Every major module should be independently replaceable.

---

## Scalability

The architecture should support future growth without requiring major rewrites.

Every expensive subsystem should be capable of independent horizontal scaling.

Examples include:

- AI Processing
- Backtesting
- Report Generation

---

## Security

User uploaded code is considered untrusted.

QuantLint never executes uploaded strategy code directly.

All uploaded files must be validated before entering the analysis pipeline.

Secrets, credentials, and API keys are never exposed to the frontend.

---

## Deterministic Analysis

Financial calculations should always come from deterministic algorithms.

Examples include:

- Sharpe Ratio
- Sortino Ratio
- Maximum Drawdown
- Win Rate
- CAGR
- Volatility
- Value at Risk

Large Language Models are never responsible for mathematical calculations.

---

## Explainability

Every analysis result should include a human-readable explanation.

Users should understand:

- why an issue was detected
- why a strategy received a specific score
- how the issue can be fixed

Explainability is one of the platform's core principles.

---

## Extensibility

New validation rules, AI providers, reports, and analysis modules should be added without modifying existing business logic.

The architecture should favor extension instead of modification.

# Core Architectural Principles

The system follows a modular monolith architecture.

Although deployed as a single backend application during the MVP phase, every subsystem is designed as an independent module.

This allows future migration into microservices without significant architectural changes.

Each module owns its own responsibility.

Modules communicate only through clearly defined interfaces.

Business logic should never leak into presentation layers.

Presentation layers should never contain financial calculations.

Long-running operations should never block API requests.

Every expensive operation should execute asynchronously through background workers.

The architecture is designed to prioritize maintainability over short-term development speed.

---

# Core System Modules

QuantLint is built as a collection of independent modules.

Each module has one responsibility and communicates with other modules through clearly defined interfaces.

This separation ensures the application remains maintainable, scalable, and easy to extend.

# Analysis Pipeline

The Analysis Pipeline is the heart of QuantLint.

Every strategy uploaded by a user passes through a sequence of deterministic validation stages before AI explanations are generated.

The pipeline is designed so that every stage has a single responsibility.

A failure in one stage should not crash the entire pipeline.

Instead, failures should be recorded, reported, and isolated.

The user uploads a Python strategy through the web interface.

Supported upload methods

- Python file (.py)
- ZIP project (future)
- GitHub repository (future)

The upload endpoint should never execute uploaded files.

Every upload must first pass file validation.

---

# Stage 2 — File Validation

Purpose

Ensure uploaded files are safe and valid.

Validation includes

- File type validation
- Maximum size validation
- Filename sanitization
- Duplicate detection
- Encoding validation

If validation fails

↓

Reject upload

↓

Return descriptive error

---

# Stage 3 — Project Storage

After validation

The strategy metadata is stored inside PostgreSQL.

The original source file is stored inside Cloudflare R2.

Database stores

- Project
- Strategy
- Version
- Upload timestamp
- User ownership

Object storage stores

- Original file

---

# Stage 4 — Analysis Job Creation

The backend immediately creates an analysis job.

The HTTP request ends here.

The frontend receives

- Job ID
- Current Status

No expensive work happens inside the request.

---

# Stage 5 — Queue Processing

Every analysis request enters Redis.

Redis acts as the message broker.

Background workers pull jobs from the queue.

Benefits

- Non-blocking API
- Horizontal scaling
- Retry support
- Failure recovery

---

# Stage 6 — Background Worker

The worker becomes responsible for the entire analysis.

Responsibilities

- Load strategy
- Execute pipeline
- Handle retries
- Log progress
- Save results

Workers should be stateless.

Multiple workers should run simultaneously.

---

# Stage 7 — Static Analysis

The uploaded code is parsed without execution.

- Python syntax
- Imports
- Trading logic
- Risk management
- Dangerous functions
- Hardcoded secrets

Results are stored immediately.

# Architecture Summary

QuantLint follows six core architectural principles.

1. Modular

Every subsystem has one responsibility.

2. Deterministic

Financial calculations are never delegated to AI.

3. Explainable

AI explains results but never invents them.

4. Secure

Uploaded code is never executed directly.

5. Scalable

Expensive work runs asynchronously and services can scale independently.

6. Provider Agnostic

AI providers can be replaced without changing application logic.

Every new feature added to QuantLint should reinforce these principles rather than bypass them.
