# QuantLint Architecture Decision Records (ADR)

Version: 1.0

Status: Active

Last Updated: August 2026

---

# Purpose

This document records every important architectural and technical decision made during the development of QuantLint.

Its purpose is to prevent future contributors or AI coding assistants from repeatedly questioning decisions that have already been made.

Every decision should contain

- Decision
- Status
- Reason
- Consequences

This document is considered the single source of truth for technical decisions.

---

###########################################################

ADR-001

Project Vision

###########################################################

Status

Accepted

---

Decision

QuantLint will be built as an AI-powered Quality Assurance platform for algorithmic trading strategies.

It will NOT become

- a brokerage
- a trading platform
- a live execution engine
- a signal provider

---

Reason

The long-term goal is to become the "GitHub Actions + SonarQube" for quantitative trading strategies.

The focus is validation, explainability, risk analysis, and research.

---

Consequences

Every future feature should improve strategy validation rather than trade execution.

---

###########################################################

ADR-002

Architecture Style

###########################################################

Status

Accepted

---

Decision

The application will use a Modular Monolith architecture during the MVP.

---

Reason

A Modular Monolith is significantly easier to build and maintain for a small team.

It provides clear separation of concerns while avoiding the complexity of microservices.

---

Consequences

Every module should remain independent.

Future migration to microservices should require minimal changes.

---

###########################################################

ADR-008

AI Gateway Architecture

###########################################################

Status

Accepted

---

Decision

All AI communication must pass through a centralized AI Gateway.

No service or module should communicate directly with an AI provider.

---

Reason

The AI Gateway provides

- Provider abstraction
- Model routing
- Retry logic
- Response validation
- Prompt versioning
- Token tracking
- Cost tracking
- Failover support

This allows QuantLint to switch providers without modifying business logic.

---

Consequences

Future AI providers can be integrated by extending the gateway instead of changing application code.

---

Provider Agnostic AI

###########################################################

Status

Accepted

---

Decision

QuantLint will never depend on a single AI provider.

Supported providers include

- GLM
- Claude
- DeepSeek
- OpenAI
- Gemini

---

Reason

AI providers change frequently.

---

Consequences

Business logic should never reference a provider directly.

###########################################################

ADR-010

AI Responsibilities

###########################################################

Status

Accepted

---

Decision

AI is responsible only for explanation and recommendations.

AI must never generate deterministic financial values.

---

Reason

Large Language Models are probabilistic systems.

Financial calculations require deterministic algorithms.

---

AI may explain

- Sharpe Ratio
- Drawdown
- Risk
- Rule Violations
- Backtest Results

AI may NOT calculate

- Sharpe Ratio
- CAGR
- Win Rate
- Profit Factor
- Drawdown
- Volatility

---

Consequences

All financial metrics originate from deterministic code.

---

###########################################################

ADR-011

Rule Engine

###########################################################

Status

Accepted

---

Decision

Validation logic will be implemented through an independent Rule Engine.

Every validation check should be represented as an independent rule.

---

Reason

Hardcoding validation logic throughout the application reduces maintainability.

A Rule Engine makes QuantLint extensible.

New validation rules can be added without modifying existing rules.

---

Consequences

Every rule should contain

- Rule ID
- Category
- Severity
- Description
- Recommendation

---

###########################################################

ADR-012

Static Analysis First

###########################################################

Status

Accepted

---

Decision

Every uploaded strategy must undergo deterministic static analysis before AI analysis.

---

Reason

Static analysis is

- faster
- cheaper
- deterministic
- explainable

AI should enhance deterministic analysis rather than replace it.

---

Consequences

Static Analysis always executes before the AI Gateway.

---

###########################################################

ADR-014

Background Workers

###########################################################

Status

Accepted

---

Decision

Expensive operations must execute asynchronously.

HTTP requests should never perform

- AI Analysis
- Backtesting
- Report Generation

---

Reason

Long-running operations reduce responsiveness and scalability.

Background workers improve user experience and reliability.

---

Consequences

API routes remain lightweight.

Workers become independently scalable.

---

###########################################################

ADR-015

Deterministic Before AI

###########################################################

Status

Accepted

---

Decision

Every deterministic calculation must complete before AI is invoked.

---

Reason

AI explanations should always be based on verified numerical results.

This prevents hallucinated metrics and inconsistent reports.

---

Consequences

The AI Gateway receives completed analysis rather than raw strategy code whenever possible.

---

###########################################################

ADR-016

Immutable Reports

###########################################################

Status

Accepted

---

Decision

Generated reports are immutable.

Once generated, reports should never be edited.

A new analysis produces a new report version.

---

Reason

Immutability preserves auditability and research reproducibility.

---

Consequences

Reports become historical records.

Version history remains trustworthy.

---

###########################################################

ADR-017

Strategy Versioning

###########################################################

Status

Accepted

---

Decision

Strategies are version-controlled.

Every significant modification creates a new version.

---

Reason

Users should be able to compare analyses across strategy revisions.

---

Consequences

Analysis results always reference a specific strategy version.

---


###########################################################

ADR-018

Security First Architecture

###########################################################

Status

Accepted

---

Decision

Security takes priority over convenience.

Every feature must be designed assuming user input is untrusted.

---

Reason

QuantLint accepts user-uploaded strategy code.

Uploaded files may contain malicious or poorly written code.

The platform must never execute uploaded code directly.

---

Consequences

Always

- Validate input
- Sanitize uploads
- Validate file types
- Validate request payloads

Never

- Use eval()
- Use exec()
- Execute uploaded strategies
- Expose secrets to clients

---

###########################################################

Status

Accepted

---

Decision

The MVP will remain a Modular Monolith.

---

# Decision Review Process

Every significant architectural or technical decision should be evaluated before implementation.

Questions to consider

- Does this align with the project vision?
- Does this improve maintainability?
- Does this simplify AI-assisted development?
- Does this reduce technical debt?
- Does this preserve modularity?
- Does this improve scalability?
- Does this increase security?

If the answer to most of these questions is "No", reconsider the decision before implementation.

---

# Document Maintenance

This document is a living record.

Whenever a major technical decision is made:

1. Create a new ADR.
2. Assign the next sequential ADR number.
3. Record the decision, reason, and consequences.
4. Do not modify historical ADRs unless correcting factual errors.

Maintaining this history ensures that future contributors and AI coding assistants understand not only **what** decisions were made, but **why** they were made.
